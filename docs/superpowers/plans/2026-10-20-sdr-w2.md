Base: 0165b65e7e1b759ef3a783ba418043a97074d1fc
Test runs: scoped per task; full suite once, final task.

**Goal:** The `/sdr` skill that a user can invoke: `skills/sdr/SKILL.md`, the four subagent prompts under `skills/sdr/prompts/`, a README entry, and the synthetic two-service warrants fixture with a hand-written record at stage `decide` for the live run of spec section 12.

**Architecture:** `SKILL.md` is the procedure that the author (the main session) follows. It names the exact `sdr.py` commands of wave 1 and fills each prompt template by plain text replacement of `{name}`, as explain's lesson gates and course prompts do. One test module, `skills/sdr/tests/test_prompts.py`, ties `SKILL.md`, the prompts, `sdr.py` (`USAGE`, `STAGES`, `SECTIONS`, `ROLES`, `FACTS_TITLES`) and explain's `rungs/page.md` together, so they cannot drift. It also checks the warrants record with `sdr.py check`. The skill files are STE prose, and `ste_lint.py` checks them.

**Tech Stack:** Markdown (STE-80 profile), python3 stdlib unittest, bash (`install.sh`).

**Spec:** `docs/superpowers/specs/2026-10-20-sdr-design.md` (sections 3, 4, 5, 7, 8, 10, 11, 12). Wave map: `docs/superpowers/waves/2026-10-20-sdr.yaml`, wave `sdr-procedure`. Coverage: waived. Wave 1 plan (the `sdr.py` contract): `docs/superpowers/plans/2026-10-20-sdr-w1.md`.

- Fences in the record and the fact files start at column 0 with three backticks. A doc block that shows such a fence nested in its body uses a four-backtick outer fence.

## Review Focus

1. Two code directories with the same basename (`a/app`, `b/app`) give the same fact-file id, so one searcher overwrites the other's `explore/code-app.md`. `SKILL.md` gives the later ones `-2`, `-3`. Task 4 pins this with `test_skill_texts` (`ID_SUFFIX`).
2. The session dies while it waits at Stop 1, after `stage: frame` is written. A resume would then go on to the options stage with no approval. `SKILL.md` repeats Stop 1 on a resume at stage `frame`. Task 4 pins this with `test_skill_texts` (`RESUME_STOP`).
3. The three consilium reviewers run in parallel and write into one directory, so one can read another's report. The cold reviewer can read the consilium reports too. Each reviewer prompt closes the directory of `sdr.md` and its parent. Task 3 pins this with `test_each_reviewer_reads_only_its_inputs`.
4. A searcher writes a form that `check-facts` reads by no rule: a fenced block in `Facts`, a `~~~` fence, a `### ` heading outside `Relevant flows` (wave 1 ruling R9). The facts in that form are lost with no finding. Task 2 pins the prompt rules with `test_fact_rules_in_each_prompt`.
5. The live run's consilium and cold reviewer read code under the root. If the hand-written record lies under the root, they read a finished decision. The record lives outside `services/`. Task 1 pins this with `test_record_is_outside_the_root`.

The services are plain Java 17 (packages `fixture.orchestrator` and `fixture.executor`). They have no build file, and nothing compiles them. Each file has at most 40 lines and holds no comment line, so no word in them hints at the gap or at an option. Each fact below is on a line of its own, so that a searcher can cite it:
- `Claim.java`: a record of one claim: claim id, source system, debtor id, action (`BLOCK`, `SET_ALLOWANCE`, `UNBLOCK`, `CONFISCATE`) and amount.
- `WarrantMapper.java`: maps a claim to a warrant id. By default one claim gives one warrant. For the one source system named by a constant `"BULK"`, the warrant id comes from the debtor id, so all the claims of a debtor share one warrant. On each change of a claim, it sums all the claims of that warrant into a block total and a confiscate total. Then it sends the executor a command that holds the warrant id and the totals, and no claim id.
- `LegacyClaimWorkflow.java`: the legacy flow. It runs one workflow for each claim and notifies the end user at each step, with the claim id in the text.
- `WarrantCommandListener.java`: receives the command. It compares the new totals with the current totals of the warrant, and calls block, unblock or confiscate for the difference.
- `ExecutionEvent.java`: a record with the warrant id, the action (`BLOCKED`, `UNBLOCKED`, `CONFISCATED`), the amount and the warrant total after the action. It has no claim id.
- `EventPublisher.java`: publishes each `ExecutionEvent` to the topic `warrant.executions`.

The record `record/sdr.md` follows the record format of spec section 6. Model it on `tests/fixtures/records/valid-decide.md`, with new cites into the services:
- Header: `# SDR: How do we notify the end user of each warrant action?`, `stage: decide`, `root: /fixture-root`, `code: /fixture-root/orchestrator; /fixture-root/executor`.
- Context: one path cite for each of these facts: the one-claim-one-warrant default, the `BULK` many-to-one mapping, the command without a claim id, the fields of `ExecutionEvent`, and the legacy notify for each claim. Add at least one URL cite. Path cites are relative to `services/` (`orchestrator/WarrantMapper.java:<n>`).
- Requirements: the sources `user`, `code` and `assumption` among the FRs. One NFR with a measurable target and one with `target: unknown`. One requirement with `source: consilium sceptic`, and a fit line for it in each option.
- Options: three. `opt-a` is the smallest change: notify for each warrant action from the existing event, with the warrant total only. The other two keep the claim attribution at another place (for example, on the executor's event, or in a claim ledger of the orchestrator). Each option name has at most 40 characters, because the matrix headers render vertically.
- Consilium: the three roles. At least one role prefers an option other than the choice. One correction is `accepted` and one is `rejected`.
- Decision: the choice `fails` a requirement that another option `meets`, and `why:` names that id. One `dissent:` for each role whose preference differs from the choice. A `revisit when:` and a `next steps:` line.
- Open questions: at least one, the `target: unknown` NFR among them. Not covered: at least one line.

```python

```

Each prompt opens like `explain/course/map-task.md`: a title, then one line that says the file is a template, filled by plain text replacement of each name in braces. The level-2 sections, in this order:

```
SEARCH_SECTIONS = ("Your task", "Inputs", "What to look for", "Rules", "The fact file", "Check", "Result")
```

Contracts, by section:
- Your task: one searcher, one question (`{question}`), one fact file (`{facts}`). Write no other file.
- Inputs: the code prompt reads `{code_dir}` under `{root}`. The web prompt researches one `{topic}`. Path cites are relative to `{root}`.
- What to look for. Code (spec 7.1): the current path of the thing that the question names; where its data lives; the events and messages on that path, with their payloads; the places where information that the question needs is present or lost; constraints visible in code (transactions, ordering, idempotency keys, retries). Map only what the question touches, not a full onboarding map (spec section 13, item 8). Web (spec 7.2): prior art for the same shape of problem, the named patterns that apply, and the library or platform documentation that the options depend on, as far as `{topic}` names them.
- Rules. The code prompt holds the reading rules of "Explore the service" in `<skill-dir>/../explain/rungs/onboard.md`, as `READ_RULES` below: read only, CodeGraph first when `.codegraph/` exists in `{code_dir}` or above it, cite only lines read from disk, no secret in a snippet. It writes no onboarding map. The web prompt holds `WEB_RULES`.
- The fact file: a skeleton in a fenced block (four-backtick outer fence in the code prompt, because it nests the Mermaid fence), then the rules of the form.
  - Code: the format of spec 7.1, with the title `# Facts: {fact_id}` and the four sections `Shape`, `Relevant flows`, `Facts` and `Unknowns`. A flow is `### <flow-id>: <question>`, one `flowchart TD` of at most 25 nodes, and one `- <node-id>: <fact> | <cite>` line for each node.
  - Web: `# Facts: {fact_id}`, `## Facts` and `## Unknowns` only, with URL cites.
  - Both: a cite is `<path>:<line> | <snippet>` (code) or `<url> | <snippet>`. The snippet has at most 12 words, copied verbatim. `- none` marks an empty section.
- Check: the fenced command `CHECK_FACTS`. Fix the file for each finding line, and run the command again until it prints `sdr: ok`. Stop after 3 rounds; then end with the done line all the same, with each remaining finding line before it.
- Result: the reply ends with one line of `RESULT_LINES`. Write nothing after it, and do not copy the facts into the reply.

```

              "Never copy a password, a token or a key into a snippet or a fact.")
WEB_RULES = ("Cite only a page that you fetched.", "Copy the snippet from the fetched page.")
```

`READ_RULES` are the lines of `rungs/onboard.md`, word for word.


`REVIEW_ROUND_2` is `review-page.md`'s Round 2 wording. Its verification read keys on `-round-2.md` alone, because an sdr review has three rounds at most (spec 7.6). The lesson allows a fourth.

The report form of `consilium.md`, exact, as one fenced block (the author's call, from spec 7.4; Task 4's copy rules depend on it):

```
# Consilium: {role}
## opt-<x>
- verdict: <one sentence>
- dispute <id>: <old> -> <new> — <evidence>
## Missing requirements
- missing <FR|NFR>: <requirement> — <evidence>
## Preferred
<why, in one paragraph>
verdict: <one sentence>
preferred: opt-<x>
```

`consilium.md` contracts:
- Your task: a cold reviewer with the role `{role}`. It judges the options of a design review record against its requirements. It did not write the record and has no other context. It writes `{report}` and changes no other file.
- Inputs: `{files}`, one absolute path per line: `sdr.md` at stage `options`, then the fact files. `CLOSED_TEXT`, then "the files listed below". It can read code under `{root}` and fetch web pages to back a finding.
- Your role: `{brief}`.
- Judge: for each option, a verdict. For each fit mark that it disputes, a `dispute` line with evidence. For each missing requirement, a `missing` line with evidence. Evidence is a cite (`<path>:<line> | <snippet>` under `{root}`, or `<url> | <snippet>`) or a requirement id. The sentence `A finding without evidence is not a finding.` Judge the options as written, and name an option written to lose.
- Report: `CONSILIUM_REPORT`. One `## opt-<x>` block for each option of the record. `- none` under `Missing requirements` when there is none. The last two lines are `verdict:` and then `preferred: opt-<x>`.

`review.md` adapts `skills/explain/lesson/review-page.md` (same six sections, same round rules) to `index.html` and `sdr.md`:
- Your task: a cold reviewer of the page of one design review on `{question}`. It writes `{report}` and changes no other file.
- Inputs: `{files}`: `index.html`, `sdr.md`, then the fact files. `CLOSED_TEXT`, then "the files listed below and the report that Round 2 names". Each `<cite>` path is relative to `{root}`; read the cited file under the root.
- Hunt: assume one claim is not supported, and find it. `verdict: ok` with zero findings is the right answer for a correct page. The mechanical checks (cites, the lint, `sdr.py check`, the matrix) already ran; read for meaning.
- Checks: a numbered list of exactly five, in this order (spec 7.6): 1. a sentence that its cites do not support; 2. a page claim that `sdr.md` does not hold; 3. a recommendation that the matrix does not support: the choice fails a requirement that another option meets, and the decision does not say why that is acceptable; 4. a strawman: an option with no real pro, or a con that the cited facts contradict; 5. a dissent of the consilium that the page hides.
- Round 2: `{previous}` is `none` in round 1 (skip the section). Otherwise rule each finding of `{previous}` `resolved` or `open` against its `## Author` block, with the current source line quoted, before any hunt. A `{previous}` whose name ends in `-round-2.md` makes this a verification read: rule only, hunt for nothing new, `verdict: ok` only when each finding is `resolved`.
- Report: the rulings, then the numbered findings (file, location, the claim quoted, the source lines quoted, what is wrong, a fix in one line). `A finding without a quoted source line is not a finding.` The last line is `verdict: ok` or `verdict: fix`; `verdict: fix` when there is a finding. The author appends `## Author`; the reviewer does not write it.
