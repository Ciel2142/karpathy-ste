**Goal:** `skills/sdr/scripts/sdr.py` with four commands (`skeleton`, `check`, `check-facts`, `matrix`). Together they are the mechanical floor of a design review record.

**Architecture:** One stdlib Python script in the manner of `skills/explain/scripts/onboard.py`. A line reader turns `sdr.md` into header fields, level-2 sections and `### ` blocks, and keeps fenced blocks apart as Mermaid diagrams. Rule functions, gated by the recorded stage, return finding lines. `cmd_*` functions wrap them with the exit codes. The script imports `cite_check.fact_problems` and the Mermaid parser of `onboard.py` from `skills/explain/scripts`, and never changes them.

**Tech Stack:** python3 (stdlib only), unittest. explain's `verify.sh` and headless Chrome run in one page test.

**Spec:** `docs/superpowers/specs/2026-10-20-sdr-design.md` (sections 5, 6, 7.1, 9, 11). Wave map: `docs/superpowers/waves/2026-10-20-sdr.yaml`, wave `sdr-record`. Coverage: waived.

## Global Constraints

- python3 stdlib only. No new dependency.
- Never change `skills/explain/`. The final task runs `git diff --quiet "$(git merge-base main HEAD)" -- skills/explain`.
- Imports: at module top, `sdr.py` puts `os.path.join(os.path.dirname(os.path.realpath(__file__)), "..", "..", "explain", "scripts")` on `sys.path`, then imports `cite_check` and `onboard`. `onboard.py` itself does `import cite_check`.
- The command forms, verbatim from spec section 9, are the `USAGE` text (stderr, exit 2):

```
usage: sdr.py skeleton <sdr-dir> --question <text> --root <root> [--code <dir>]...
       sdr.py check <sdr-dir> [--root <root>]
       sdr.py check-facts <file> --root <root>
       sdr.py matrix <sdr-dir>
```

- Exit 0 means ok, 1 means findings, 2 means a usage error or an unreadable file. Usage text and every exit-2 line go to stderr. Finding lines and the summary go to stdout.
- Output: one finding per line, each with a prefix that says where (`header:`, `section:`, `title:`, `req <id>:`, `constraint #<n>:`, `cite <scope>#<n>:`, `flow <heading>:`, `diagram <flow>:`, `node <flow>/<node>:`, `fact <flow>/<key>:`, `option ...:`, `fit <opt>/<id>:`, `consilium <role>:`, `decision:`, `page:`). The last line is `sdr: ok` or `sdr: <n> findings`.
- Stages, in order: `intake explore frame options consilium decide page review done`. The record holds the last finished stage on line 2. The "Ends with" column of spec section 5 is authoritative.
- Sections, in order: `Problem`, `Context`, `Functional requirements`, `Non-functional requirements`, `Constraints`, `Non-goals`, `Options`, `Consilium`, `Decision`, `Open questions`, `Not covered`.
- The stage that first reaches each section (derived from spec section 5): `frame` reaches Problem, Context, both requirement sections, Constraints, Non-goals and Options (shortlist form). `options` reaches the full Options blocks. `consilium` reaches Consilium. `decide` reaches Decision, Open questions and Not covered. `page`, `review` and `done` add the matrix comparison with `index.html`.
- Roles: `architect`, `operator`, `sceptic`. Marks: `meets`, `partial`, `fails`, shown as `✓`, `◐`, `✗`.
- Cites: a snippet has at most 12 words. A path cite is checked under the root by `cite_check.fact_problems`. A URL cite (`http://` or `https://`) is checked for form only.
- Mermaid: one `flowchart` block, at most 25 nodes (`onboard.MAX_NODES`), as parsed by `onboard.mermaid_kind` and `onboard.mermaid_nodes`.
- Owned paths: `skills/sdr/scripts/`, `skills/sdr/tests/test_sdr.py`, `skills/sdr/tests/fixtures/records/`, `skills/sdr/tests/fixtures/pages/`. No `SKILL.md`, prompt or README change in this wave (wave 2 owns them).
- Scoped test command: `cd skills/sdr && python3 -B -m unittest discover -s tests`. Never commit `out/` or `.beads/`.
- The record's prose is not linted.

## Review Focus

1. Lines inside a fenced block (an option's Mermaid diagram) are never read as a section, a block, a key or a fit line, even when one starts with `## `, `### ` or `- fit `. Task 1 pins this with `test_fenced_lines_are_not_structure`.
2. A record saved with a byte order mark or CRLF line endings checks the same as an LF file. Task 1 pins this with `test_bom_and_crlf_read_as_lf`.
3. A fit line written with ` - ` (hyphen) instead of ` — ` (em dash) gets a finding that names the expected separator. It is not read as a mark error and it does not pass. Task 3 pins this with `test_fit_hyphen_separator_named`.
4. A `why:` that names `NFR-12` does not satisfy a required `NFR-1`: requirement ids match as whole tokens. Task 4 pins this with `test_why_token_match_is_exact`.
5. `<`, `&` and `"` in requirement texts and option names come out escaped in the matrix. A second run is still byte-identical, and the stale check still passes. Task 5 pins this with `test_matrix_escapes_html`.

- [ ] **Step 3: Implement the reader: `read_sections`, `parse_record`, `read_record`, `reached`**

- `parse_record` removes a leading `﻿` and splits with `str.splitlines()`, so CRLF reads as LF. `header` is lines 1 to 4, padded with `""` when the file is shorter.
  - `question`: the text after `# SDR: ` when non-blank.
  - `stage`: the word after `stage: `, kept even when it is not in `STAGES`. `None` when line 2 has another form.
  - `root`: the path after `root: ` when `os.path.isabs`.
  - `code`: `[]` for `code: none`, or the `; `-separated paths when each is absolute. `None` otherwise.
- `read_sections(lines, first)` reads from the 0-based index `first`. A line that starts with `## ` opens a section. A `### ` line opens a block of the open section. A line that starts with ``` opens a fence, and the next such line closes it. A closed fence whose info string is `mermaid` becomes `onboard.Diagram(<opening line>, mermaid_kind(body), mermaid_nodes(body), body)` on the open block, or else on the section. Other fences are dropped. An unclosed fence closes at the end of the file. `lines` holds the stripped non-blank lines outside fences, with their 1-based numbers. The `### ` heading line is never one of its block's lines.
- `read_record(sdr_dir)` reads `<sdr_dir>/sdr.md` as UTF-8. `OSError` or `UnicodeDecodeError` raises `SdrError("sdr: cannot read <path>: <reason>")`.
- `reached(stage, at)` is `STAGES.index(stage) >= STAGES.index(at)`.

- [ ] **Step 4: Implement `check_record` for the header and the sections**

Order of output: header lines, then section lines, then, when the stage is known, the content lines that later tasks add, in this order: cited lines (Task 2), options (Task 3), consilium and decision (Task 4).
- Header lines:
  - `header: line 1 is not "# SDR: <question>"`
  - `header: line 2 is not "stage: <name>"`
  - `header: unknown stage <word>`
  - `header: line 3 is not "root: <absolute path>"`
  - `header: line 4 is not "code: <absolute dirs>" or "code: none"`
- Section lines, as in `onboard._section_lines`:
  - `section: missing <title>`, in canonical order.
  - Then, in record order: `section: <title> twice`, `section: <title> out of order` (its index is lower than the highest index seen so far), `section: unknown <title>`.
- When the stage is in `STAGES`, for each known section that is present (first occurrence). A section is "pending" when its lines are exactly `pending` and it has no blocks. It is "empty" when it has no lines and no blocks.
  - An unreached section that is not pending: `section: <title> not pending at stage <stage>`.
  - A reached section that is pending: `section: <title> pending at stage <stage>`.
  - A reached section that is empty: `section: <title> empty, write none`.
  - The content rules of later tasks skip a section that is missing, or that is reached and pending or empty. Such a section gives only its section line; for example, an Options section that is pending at stage `frame` gives no option-count line.

- [ ] **Step 5: Implement `cmd_skeleton`, `cmd_check` and `main`**

- `main` dispatches on `argv[0]` (`skeleton` and `check` in this task). An unknown or missing command writes `USAGE` to stderr and returns 2. `SdrError` writes its line to stderr and returns its code. An argparse error raises `SdrError(USAGE)`, as `onboard._Parser` does.
- `cmd_skeleton`:
  - The question is `" ".join(text.split())`. Empty: usage, exit 2.
  - Root and code dirs go through `os.path.abspath(os.path.expanduser(...))`.
  - A root that is not a directory: `sdr: cannot read root <root>`.
  - A code path that is not a directory: `sdr: cannot read code dir <dir>`.

- `cmd_check <sdr-dir> [--root <root>]`:
  - The root is `--root` or else `record.root`. Neither: `sdr: no root: give --root or a "root:" line`, exit 2. Not a directory: `sdr: cannot read root <root>`, exit 2.
  - Print the findings, then the summary line. Exit 1 when there are findings, else 0.

- [ ] **Step 3: Implement `parse_fact`, `cite_problems` and the frame-stage rules in `check_record`**

- `parse_fact(n, line, text)`: `text` is the bullet without `- `. It is split on ` | `. A cite needs exactly 3 parts: the where part is a URL (`https?://\S+`) or `<path>:<line>` (`(.+):([0-9]+)`, line >= 1), and the snippet is non-blank. Then `where` and `snippet` are set. Otherwise both are `None`. `fact` is part 0, stripped.
- `cite_problems(where, snippet, root)`:
  - A URL gets `snippet has <k> words (max 12)` when it has more than 12 words, else no problem.
  - A path gets `cite_check.fact_problems(path, int(line), snippet, root)`.
- Only from stage `frame` on, and only for a section that is not `none`. `<n>` is the 1-based index of the bullet in its section. Cite problems print as `cite <section title>#<n>: <problem>`.
  - Context: each `- ` line is a fact. No cite: `cite Context#<n>: no cite`.
  - Requirements: parse the line as `<ID>: <text>`, then the ` | `-separated fields. The k-th id line of `Functional requirements` must be `FR-k`; in `Non-functional requirements` it must be `NFR-k`. The lines, by rule:
    - `req FR#<n>: no id` (`NFR#` in the NFR section): the line has no id of its section's kind. The line gets only this finding and does not count in the sequence.
    - `req <ID>: expected <KIND>-<k>`: the line is the k-th id line and holds another id.
    - `req <ID>: no text`.
    - `req <ID>: no target`: an NFR whose first field is not `target: <non-blank>`. A `target:` field is consumed even when it is blank.
    - `req <ID>: no source`: the next field is not `source: <value>`.
    - `req <ID>: unknown source <value>`: the value is not one of `SOURCES`, nor `consilium <role>` with the role in `ROLES`.
    - `req <ID>: source code needs a <path>:<line> cite`: source `code`, and the rest is not exactly a where part and a snippet with a path where part.
    - `req <ID>: source web needs a URL cite`: source `web`, and the rest is not exactly a URL where part and a snippet.
    - `req <ID>: source <value> takes no cite`: any other source with more fields after it.
  - A cite that passes form goes through `cite_problems`.
  - Constraints: each bullet is `<constraint> | source: <value>[ | <cite>]`, with the same source rules. The prefix is `constraint #<n>:`.
- `requirements(record)`: the lines with a well-formed id of their section's kind and a non-blank text. FR lines come first, then NFR lines, in record order. `text` is the part after `<ID>: `, without the fields.
